## The cause: the reader's path limit

The start is not the cause. Between the bar (rooms 33 and 28), the bar with room 38, the bar with room 35 and k = 1,
every pair's shared facts (667 to 1,463) have the same start values, and no start has a NONE value. A bigger scope reached less
than a smaller one: with goal state:316 = 1 (the kitchen door open), the bar plans 6 steps, k = 1 had no plan, and
taskcore's step (d) proved the goal unreachable.

The machine ends a path where a fork would pass PATH_LIMIT (1,024 paths). reader.py's rule splits such a run on its
first fork on a read, but not when the run forked more on non-facts than on facts, and not past 2 levels or 4 parts.
The paths the limit ended are then dropped, with no record.

The smallest case is rooms 33, 28 and 35 (seed 1, `--elsewhere --live-locals`):

- Room 35's scripts make facts of what is constant in the bar: every object's classes (a global's `setClass` on its
  argument) and var:196 (a write through `Var[184 + Local[1]]`).
- Room 28's entry tests var:196 and loops over five objects' owners. The walk through the kitchen door (the sentence
  script's wait at 736, then the door's walk entry loads room 28) makes 354 paths in pass 1 and 1,024 in pass 2,
  with 532 cut. It forked 506 times on facts and 1,353 on non-facts, so it was not split.
- The kept room-28 paths need class 16 or 15 of the door at 1. The start has both at 0, and nothing in the scope sets
  them. So 0 of the 85 writers of state:316 = 1 apply.

Part I has the same cause. A partial reading of the Part I scope (the walks to room 33's three doors, room 33's
sentences, the sentence script's events) cuts all 9 door walks (3 doors, 3 waits), 357 to 489 paths each, none split.
The kept room-28 paths of the door walk need the door's classes and var:33 = 202 and var:111 = 2; the start has the
classes at 0, var:33 = 2 and var:111 = 11. From the start the relaxation reaches rooms 33 and 38 only; 1,728 writers of
room 28 and 1,200 of room 35 apply none. On the VM the longest jobs were these walks, split once, each part past the
limit again.

D10 names a start-state bug fix. The cause found is this limit; the start state was right.

## The fix: split until no part passes the limit

A reader switch, `split_limit` (reader-scope `--split-limit`, reader-port `--switches split_limit`), off by default.
With it off, the reading stays reader.py's, as D7 requires.

- A run past the path limit is run again once per value of its first fork on a read, that fact pinned. A part that
  passes the limit is split again. No depth cap, no budget cap, no non-fact rule.
- A part that passes the limit with no fact left to split on stops the reading, naming the job. So does a path the
  step limit (5,000 steps) ended.
- Why it is exact: in any state the engine runs one path of the job. The parts' preconditions divide the job's states
  by the pinned fact's values. They do not overlap and together cover them, and each part runs the same code. So
  the parts' records cover every state the job can start in, the start included. No path is dropped.
- Under the switch the machine half hands over no path of a cut run, which the Builder only splits.

A larger limit is no fix: at 16,384, 10 runs still pass it in bar + 35.

## What this means

1. Part I attempt 2's "no plan" came from the reader dropping the paths the path limit cut, not from the start, the
   goal or the planner.
2. With the switch, the reading covers every state each job can start in, as D4 and D9 ask: no path is dropped by the
   limit, and a run the rule cannot split stops the reading instead of losing states.
3. Other drops of the same kind remain, counted but not fixed: lists folded past SIG_LIMIT (22 at k = 1), only the
   first args-0 event at a wait point, and the paths that end "spin", "error" or "nesting" (1,794, 150 and 8 at k = 1).
