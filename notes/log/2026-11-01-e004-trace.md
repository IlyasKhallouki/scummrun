# 2026-11-01: E004 plan step B1, trace validation with the engine's explanation

Question: when the model and the engine disagree, can the engine say where and on which value, automatically, for at
least 90% of run B's rejected moves and refuted predictions? And how strictly do the window search's runs match the
reading's records when every slot run must be explained by one record?

Method and lemmas: `experiments/E003-path-through-cloud/trace-validation.md`, written before the code; the rules the
first runs called for are listed there with the case that showed each. Code: `trace_explain.py` (the library) and
`trace_check.py` (the runs), the bridge's `segment` and `explain` controls (`patches/`, speedrun_explain.cpp), and
`Branch.segment`, `runs`, `explain` and `explain_log` (`src/speedrun/control.py`). Numbers:
`results/trace-check-off.log`, `results/b1-runb-seed1.log`, `results/b1-window-*.log`, `results/b1-locate.jsonl`,
and the cause list `results/b1-causes.tsv`.

Prediction (the plan, before the runs): at least 90% of run B's misses get a cause (an opcode and the engine's value);
the logs stay in kilobytes; 0.5 to 1 CPU h.

Answer: on seed 1, run B's recorded inputs stay on run B's moves for the first 56 rows (51 counted moves). There the
model check has 28 misses: 2 rejected moves, both floor clicks (outside V), and 26 refuted certain predictions (134 of
160 are right). All 26 refuted predictions get an automatic cause: 26 of 28 misses (92.9%), 26 of 26 inside V. 20 are
of class split (all on a wait: the move's done frame comes before the slot reaches the write), 6 of class semantics.
On the window runs, 10,196 slot runs resumed at a wait point: 1,649 explained by exactly one record, 2,819 by more
than one, 328 stutter, 3,250 at points with no record (every one invisible to the task), 2,150 unexplained; 2,122 of
those fall in groups whose first run got a cause. Of the 38 plan steps the window runs counted as matched, 14 match
strictly on their own run.

  are off by default.
- Lemma O's test (`trace_check.py check-off`): run B's inputs from boot on seed 1, frames 1 to 3,235, three engines in
  lockstep: the shared window build, the new build with the controls off, and the new build with `segment` on from boot

  locals and the exact object) on 0 and 0; the three trace.jsonl files are equal. The third engine gave 15,230 runs and
  271,939 explain entries, none dropped. Opcodes whose `_currentScript` was not their run's slot: 0.
- Cost: `segment` and a `runs` call add 0.054 ms to a frame's round trip (0.634 ms off, 0.688 ms on; 7.4 runs a frame).

## What the causes say

- Most of run B's refuted predictions are the done frame, not a wrong path: 20 of 26 are a slot still waiting. The
  model check's "certain at done" needs the time a slot still waits as a value.
- The input script is the main semantics cause in run B (3 of 6): row 5's sentence skips it.
- In the window runs the largest groups are one fact the room load writes (var 70), WaitForCamera records that only
  block, positions the door logic and a polling loop test, and a recursive start's second instance.
- Lemma X's "first opcode off the path" uses the IR's control flow; for an event record it stays within one run. Two
  groups (28 runs) end with a predicted write that is not in the run and no branch off its path.
