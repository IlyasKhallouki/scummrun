# 2026-10-25: E003 fix round 1, F10: the slots' locals at a replan

Question: the bridge dumped no script locals, so every slot live at a replan had unknown locals (args 0) and the
planner chose among its unknown-locals events. With the locals dumped, does a replan know each live slot's list,
and does the new dump change anything else in the engine?

Sources: patches/0001-scumm-add-speedrun-bridge.patch (fr1-c), bridge_locals.py, replay.py, replay_part1.py,
packed_reading.py, scumm/reader (builder.rs, task.rs, reader_scope.rs). Results in
`experiments/E003-path-through-cloud/results/` (`bridge-locals-check.log`, `bridge-locals-kitchen-replans.log`,
`replay-part1-bar-door-rust.log` and its two json files).

## The bridge

A new switch, SPEEDRUN_DUMP_LOCALS (EngineConfig.dump_locals), adds two fields to the state dump: per live slot its
25 locals (vm.localvar, script.h:76, 136), per cutscene level its cutSceneData (script.h:131; script.cpp:1640,
1658). Nothing else reads the switch. The bridge marker stays v3: no timing changes.

Built from the pinned tag with the new patch, with --no-reset, in its own folder (17 files compiled, 29 s), not in
the shared build/scummvm.

Three engines played recorded inputs from boot in lockstep, one frame at a time: the shared build, the new build with
the switch off, and on. At every frame the stop status and the whole state dump were compared.

| inputs | frames | status differs | dump differs, switch off | dump differs, switch on, new fields out | traces equal |
|---|---|---|---|---|---|
| room 33, seed 1 | 3,095 | 0 | 0 | 0 | yes |
| rooms 33 and 28, seed 1 | 3,428 | 0 | 0 | 0 | yes |
| the kitchen run's inputs | 13,675 | 0 | 0 | 0 | yes |

The live slots seen had a nonzero local in 17% (room 33), 45% (bar door) and 83% (kitchen) of the frame-slot pairs.

## The replan rule

At a replan each live slot gets the `args:` number of the list the reading built whose locals its dumped locals
match at its wait point: every dumped local equals the list's (0 where the list lacks it), or the list's local is
unknown and allows the value; the cutscene count and data are equal. This replaces "copy the plan's number when the
slot is where the plan put it". A slot no list matches is read again: the Rust reader reads the scope again from its
start with that slot's event built from its dumped locals, and the harness goes on with that task.

The reading's files gain a lists file (5,166 lists on rooms 33 and 28; 5,409 on the kitchen).

## Results

Rooms 33 and 28 from seed 1. The Rust reader's reading (reader-scope, 3 threads, 30 s) equals the Python reader's
(2,434 s): 66,106 records and 65,592 actions with the same preconditions, effects and action lines. With the switch
off both runs on it repeat the committed runs step for step.

| run | replans | live slots at args 0, before | after | what happened at the replan |
|---|---|---|---|---|
| full model | 0 | none | none | goal at frame 3129, as before |
| control | 1 (frame 6376) | 3 | 0 | local 202 and global 23 match a list; global 159 is read again |

Global 159 at offset 5 writes nothing with or without known locals. After the reading again its only args-0 record
(it wrote just `args:script:159 := 0`) is a no-op and goes, so the task has no `args:` fact for it. The reading again
took 84 s (38 s reading, 45 s for the files). The control's plan 1 stays unsolvable because of the ban, so the run
is the same; both runs verify from boot with 0 differences.

The kitchen run (9 replans, 69 live slots at args 0 in all), its recorded inputs played to each replan on the new
build with the dump: 58 of the 69 slots match a built list. 11 would be read again: global 159 at every replan and
room 28's local 207 at two. Nothing was planned here.

## What this means

1. The replan no longer guesses locals for slots the plan did not start: on the kitchen 84% of them match a list the
   reading already built, so a replan reads again only a few slots.
2. Reading the whole scope again costs a full reading and its files per such replan (84 s here). A reading kept in
   memory that adds only the new events would be the next step if replans get frequent.
3. The bar-dialog test of fix-round1.md F10 (the restored VAR_VERB_SCRIPT equals the engine's) is not run yet: no
   plan in rooms 33 and 28 goes through a dialog.
4. The first plan still starts with args 0 for the slots live at the start: the reading's start has no locals.
