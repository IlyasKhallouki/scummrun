# 2026-10-26: E003, replanning without reloading the reading

Question: at every replan the harness ran taskcore from the packed file again: load, bans, start check, fold,
reductions, writer. On Part I (11.9 GB, 3.9 million actions) that was 213 s to load, 69 s to fold and 141 s to
reduce, at 13 to 26 GB, and the start check ran two such passes. Can one long-lived taskcore keep what does not read
the start, give the planner the same input, and what does a replan then cost?

Prediction (made when the design was fixed, before any measurement): the files are the same bytes, because the kept
part is the same code run on the same task; a replan then costs (d) and what follows it, which is small where (d)
cuts most of the task.

Method: branch `noreload` from main e926bd2. `taskcore serve` (taskcore/src/serve.rs, README "Replanning without
reloading"); `plan_fd.plan_taskcore(serve=True)`, the harness's `taskcore_serve` and `replay_part1.py --serve`, all off
by default. `serve_check.py compare` runs, per recorded replan, main's `taskcore sas` (sha1 25738cbf, before), the new
binary's `sas` (14882d1e) and one `serve` process (after), and compares their files. The laptop was shared: load 12 to
20 on 8 cores from other jobs, each of ours one thread at nice 10, before and after interleaved. Wall times are about
2 to 3 times an idle machine's; CPU seconds are given next to them.

## What reads the start

The start enters `taskcore sas` at two places only: the start check, and reduction (d). The start file's start is
pushed onto the task's starts after the load, and nothing before (d) reads starts.

| step | reads | kept by the server? |
|---|---|---|
| load | the file | yes, once |
| bans | the input actions, the bans | per ban set (a view: the pieces only) |
| start check | the start, the banned task | redone (only when a start value is outside a domain) |
| the facts (e) needs, for the operator table | the banned task, the goal | per (bans, goal) |
| fold | the actions' sets, the domains | per (bans, goal) |
| normalize, (a), (c) | the actions | per (bans, goal): the loop's first round up to (d) |
| (b) | the actions, the goal | per (bans, goal): the same round |
| (d) | the start | redone |
| (e), (f), the later rounds, the second fold, the writer | (d)'s result | redone |

(e) (relevance to the goal) and (f) read no start either, but the loop runs them after (d) in its first round. Run
before (d), each is still exact for every start, but (d) then sees another task: its relaxed reachability can reach
fewer values (an effect whose condition is on a precondition fact can fire there on a value only an action (e) drops
writes), and the first round's (f) then compares other sets and can keep the other of two equal actions. The file
would differ, and so could lama-first's plan. So the server keeps exactly the steps `sas` runs before (d), and the
file is the same by construction: `reduce::run` is now `prefix`, (d), `finish`, the same steps on the same task.

Bans and the goal come before the fold, so every kept step depends on them. A request with other bans or another goal
rebuilds the kept part from the loaded task in memory; no file is read again.

Two changes to taskcore keep its files and make it lighter (pure engineering, checked below): the reductions rewrite
the task in place (a reduction's peak is the task, not twice it), and (e) reads again only the effects whose fact
gained a needed value since the action's last visit (the same sets in the same order; on a k = 1 replan 1.3 s
instead of 9.7 s).

today (the VM): 213 s to load, 69 s to fold, 141 s to reduce, 13 to 26 GB per pass; the first plan's taskcore took
438 s and the start check two passes of 420 s.

| start check | two passes, 420 s each | two kept requests |

The k = 2 ratios are measured; the Part I numbers are those ratios applied to the VM's, not a run. 500 replans were
about 60 hours of taskcore before; with the server they are about 420 s, plus 500 times 3 to 23 s, plus 210 s per ban.

on the kitchen, with all of it reachable, it was 5 CPU s.

Surprises: the k = 1 and k = 2 readings do not reach the kitchen door open (state:316 = 1) from seed 1's start even
with deletes ignored, while the bar door reading (rooms 33 and 28) reaches it with a 6-step plan
(results/replay-part1-bar-door-seed1.json). Not looked into here. And Fast Downward's landmark dump lists the same orderings in another order from run
to run on one file (three runs agreed, a fourth did not).

## What this means

1. The planner input is the same bytes with and without the server, on every recorded replan and every random case,
   and the harness's runs are the same runs. The switch changes time and memory only.
2. A replan no longer loads, bans, folds or reduces the whole reading: it redoes (d) from the new start and what
   follows. On k = 2 that is 0.4 to 2.0 CPU seconds against 105 to 164; on the kitchen, where (d) keeps most of the
   task, 5 against 13 to 15.
3. A new ban rebuilds the kept part from memory (the fold and the loop up to (d)): about a first request's cost, never
   a reload.
4. The start check's two modes are two requests on the same server; the first plan then keeps what they built.

Decision: the next runs use `--serve` (replay_part1.py).
