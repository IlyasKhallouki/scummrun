# 2026-10-25: E003 step 5, the replay harness on the kitchen

Question: does a plan the planner finds from the model hold up in the real engine when played with real
clicks, and what does the harness have to do when it does not?

Sources: replay.py 5ecab7dae847, replay_kitchen.py 4d3136c15cb3, on the frozen reader.py 94d495853f07 and
model.py cc630446bdbe (sha1 prefixes). Results in `experiments/E003-path-through-cloud/results/`
(`replay-kitchen.log`, `replay-kitchen-all.json`, `replay-kitchen-no211.json`). Built, reviewed by a second
agent that re-ran every number, then fixed; the numbers below are from the fixed harness.

## Setup

- Start: run B's inputs to frame 235 put the engine at S1#7's pre state; 0 of 3,651 facts differ from the
  ground truth.
- Task: the kitchen task (rooms 28 and 41), goal owner of the meat = ego. The reading gives the same 72,256
  records as before.
- Each step is played through `Executor.play()` with no fork: a sentence is the verb key and clicks, a dialog
  line a click, a skip Esc, an event a wait with no input. Nothing is pushed or written into the engine.
- Two plans: the main one (7 steps), and a variant with the cook's timer event (local 211) left out (15
  steps).

## Why the clicks failed: the room's input script

The model starts every sentence in the sentence script (global 2). In the engine a click in the room goes
to the room's own input script first (verbs.cpp:689, script.cpp:1482). In the bar that is local 202, which
hands any click on the kitchen door to local 203. Local 203 walks ego to the door and tests the cook's room
and x ([000E]-[001E]), with three outcomes:

- cook in the bar at x > 310: it starts locals 215 and 11 and stops ([0025]-[002B]);
- cook in the bar at x <= 310: it stops locals 216 and 217 and chains to script 4, which queues the sentence
  ([0030]-[0055]); this is the only path that reaches the sentence script;
- cook not in the bar: it waits for ego, runs the door's own entry for the verb and stops ([003A]-[0053]),
  with no sentence script.

So the record for "walk to the door" holds no test on the cook's position, because the reader never ran
local 203. Every room with its own input script can fail the same way.

The variant shows the other side: the door's Open entry started the provoke chain (locals 214, 212, 216) as
the scripts say, but from local 203, not from the sentence script, so the harness did not recognise it.

## What the review changed

The first version banned the walk at the values the record tested (bit:6 = 0, room 28), and that left no
plan. The review showed the same walk reaches the goal at exactly those values when the cook is away (frame
674, goal at 725, 58 inputs from boot, 0 differences). The rules now are:

- A record none of whose writes ever held never started its path, so it is not banned: it is retried 3 times
  after 60 frames, then replanned with no ban.
- Checks are evaluated in the engine at the input: the sentence script's variables (only in its own code),
  its locals 0-2, VAR_EGO and the actor getters. That covers 68,182 of the 73,433 checks on input records.
  A failing check is never a ban. A failing position check on a moving actor is waited for.
- Waits the plan puts after an input but that do not depend on it are played first; the cook's timer now
  goes before the walk in all 10 plans.
- A click counts as taken only if a slot changes on its frame or the next.
- If the plan's next events rewrote what differs within the window, the step counts as matched (ego already
  at the door: the sentence script passed its predicted wait in one frame).
- A planner timeout is recorded as a timeout, not as "no plan".
- An Executor error is played once more, then logged as an interface failure with no ban.

## What this means for Part I

1. The reader must run a click through the room's input script before the sentence script. This is a model
   fix; by D7 it is made in the Rust reader after the port.
2. The engine's path to a result can differ from the plan's (the variant's provoke chain); the harness only
   follows it as far as the next event that explains the mismatch.
3. Planning took 107-221 s per replan on the Python task, 15 to 30 hours for Part I's 500 replans. The Rust
   task core plans the kitchen in 3-9 s.
4. The bridge dumps no script locals, so 2-6 live slots have args 0 at every replan.
5. Some checks cannot be evaluated at replay yet: getDist, the WaitFor checks, messages and random draws.
6. Not built yet: the control run, starts from boot on seeds 1-5 and 31-35, landmarks and Part I goal counts
   in the report, dialog lines clicked by verb id (the reader lists verbs 109 and 110, the Executor clicks
   120-128 by text).
7. The Executor assumes ego is actor 1; the harness guards this (`EXECUTOR_EGO`).
8. Run B's own S1#7 also went through local 203, and step 3's check accepted that move: the check compares
   end facts only, so it does not see which script did the work.

## Addendum: replanning through the Rust task core

The harness now plans through taskcore (fold, exact reductions, bans and the replan start passed as files;
`results/replay-kitchen-taskcore.log`, `results/taskcore-bans.log`). On both kitchen plans the run is the same
as with the Python planner: the same inputs on the same frames, the same steps, the same engine trace, and verify
from boot gives 0 differences.

| | main plan: Python / taskcore | variant: Python / taskcore |
|---|---|---|
| task written, per plan | 0-134 s / 6.8-19.7 s | 0-120 s / 6.1-7.3 s |
| planner (lama-first), per plan | 120-187 s / 2.1-3.0 s | 107-221 s / 2.0-3.6 s |
| planning in all | 1,615 s / 128 s | 1,767 s / 118 s |
| operators | 583,670 / 17,823 | 583,662 / 17,820 |

- A ban means the same in both: Python's ban plus write_sas and taskcore's `--bans` with folds and reductions off
  give the same bytes on 8 kitchen files (four ban sets, two tasks) and on 824 of 1,000 random tasks with random
  bans (the other 176 raise in both). On the reduced banned files, Fast Downward's optimal cost equals the banned
  task's own, and every lama-first plan runs on the unreduced banned task.
- lama-first on the reduced task gives 10- and 18-step plans instead of 7 and 15. The extra steps never played
  here. Anytime LAMA with a 30 s cap gives the 7-step plans.
- At kitchen size, 500 replans cost about 1.5 hours of planning, against 15 to 30 hours before.
- No ban has yet been played in the engine through taskcore: both runs ended with 0 bans.
