# 2026-10-22: E001 step 1, answer key and baseline

Question: is the answer key sound, and how well does the quick backward regression score against it?

Prediction: none. This step measures the instrument and the starting point, not the method.

Method:
- Key: `experiments/E001-goals-from-scripts/answer_key.py`, rules K1-K4. `key.json` sha256 `625462f6ff4839d0f5821a9eaf6acf6f80fb307aa7fc944fd71943049a270ad9`.
- Baseline: `baseline.py`, the autonomy probe's `regress3.py` unchanged. Its starting fact, Bit[565], was picked by hand.
- Scoring: `score.py`. Next to recall it reports the size of what the analysis hands over and a reference "dump": every fact any player action writes or tests, with no analysis.
- Review: a workflow with four reviewers (generality, dropped facts, kept facts, scorer) and a skeptic for every proposed change, 27 agents in all. Only rules that would apply unchanged to another SCUMM v5 game were considered.

Result (`experiments/E001-goals-from-scripts/results/step1-baseline.json`):

|---|---:|---:|---:|---:|---:|---:|
| Baseline | 241 | 35/99 | 0/21 | 23/42 | 1/7 | 24/70 (34%) |

A random pick of 241 facts from the dump would get about 9.7, 2.4, 4.3 and 0.7 hits on Parts I to IV.
Part IV is scored out of 7 because the baseline's starting fact is not scored.

The key: 329 distinct route facts, 170 kept (Part I 99, II 21, III 42, IV 8). Dropped: travel 92, engine
bookkeeping 42, earlier steps of counters 25. The earlier quick figure (60 of 216, about 28%) used an
uncleaned key.

Surprises:
- The first key relied on a hand-written list of MI1 variable numbers (`search.TRANSIENT_VARS`) inside
  the milestone code. It removed 33 facts before any rule ran and they were not listed anywhere. Two general
  rules replace it: vars the engine's hook scripts write, and vars an input script copies from the click
  arguments. The key came out the same, so the list was right, but it had been a hand choice.
- Recall alone can be gamed. The dump finds all 21 Part II facts with no analysis at all, so the plan's
  thresholds need a size control.
- K4 kept the wrong "last value" when a var returned to an earlier value (Var[228], Var[262]). Fixed.
- K4 had dropped two values the game tests for: Bit[426] = 1 (the navigator's head is out, needed for the
  catacomb counter) and Var[285] = 3 (selects the pirate fights). K4 now keeps an earlier value that a
  script assigns as a constant and a condition tests.
- Part III scores higher than Part I (55% against 35%). Its goals sit mostly in object handlers, which is
  all the quick version reads.

Known noise left in the key, with no general rule to fix it:
- Part I: the storekeeper being out of the store (actor 11 in room 0) gates the safe but is dropped as
  travel. Var[221..224], the safe combination, are random draws that depend on the seed. The pamphlet
  and brochure (901, 903) are side effects of a cutscene and nothing uses them. Bit[347], Bit[447] and
  Bit[421] only stop their own block from running twice.
- Part II: the fuse appearing (S4#71) is in the route only as an actor's position, so it is not in the key.
- Part III: the same for the dam blast (S5#16). Two "script is running" facts (scripts 148 and 96) stand
  in for the goals they lead to.
- Part IV: Bit[537] is internal to the ending cutscene.
- Doors that only need opening stay in the key. Opening one is a lasting change the player makes, even
  though it mostly serves travel. Reviewers proposed a rule to drop unlocked doors (9 facts); not adopted.

Also not adopted: a rule for random-draw vars and one for once-only flags (both affect Part I only, so
they are listed above as noise), a filter on object states nobody reads (it would delete real stand-ins
for touchability), cutting facts after the route's last verb (it would only touch held-out data), and a
filter on items nothing uses (that is the analysis's own reachability test and would bias recall).

Deviation from the plan's no-peek rule: the key was revised after the baseline's held-out totals were
known, and some reviewer outputs named individual held-out facts the baseline missed or reached (for
example Var[141], Var[143] and Var[293] missed, the class change on object 178 reached). The revisions
are general rules, a skeptic checked each one for favouring the method, and the facts seen concern the old
probe, not the analysis to be built. From here on the key is frozen: `score.py` refuses any other `key.json`.

Decision: the success threshold gets a size control before step 2 starts.
