# Re-routing over what the search explored

A research report made for E031's plan (2026-11-16) by a reading agent; its claims were used in the plan after the plan's critics checked them. Evidence paths are as the agent gave them.

## Findings

### 1. What a kept stop records, and how many states that makes. The four legs hold 58,276 distinct stops (58,279 lines; each later leg's first line repeats the previous leg's top stop). By what is recorded they collapse to 3,400 states of (room, objects ever owned, news keys won on the way). The tree is one chain of gains: only 85 distinct object sets exist in it, 58 of them on the end path.

- **Evidence:** Each line of /var/tmp/fast-mi/direct/full5/leg00..leg03/nodes.jsonl holds id, parent, depth, frame, room, level (objects gained in this leg), owned (a count, relative to the leg), class, how (the trial's name), novel (at most 12 labels), news, ever, and its own input events. It holds no tick, no ego position, no facts, no digest, no RNG. Distinct values over all stops: rooms 90; object sets 85; cumulative news sets 1,116 (252 on the path); objects+news 1,203 (258 on the path); room+objects+news 3,400 (571 on the path, 1,149 held by one stop only, the largest by 1,189 stops); 3,961 with the leg's owned count added. Scripts: /var/tmp/fast-mi/e031-research/rr2/g.py and the a*.py, b*.py, c*.py, d.py files beside it.
- **Why it matters:** The files give a coarse route graph (17 stops per state on average). Inside one recorded state the stops still differ in position, object states, toggles and variables, so any merge by these keys is a proxy that only the engine can confirm.

### 2. The recorded news is not the set of facts a stop holds. It is written only at a stop that begins a new line of flags, lists only what that one trial changed, and leaves out flags once seen unset. So the files give a lower bound on held facts, never the facts themselves.

- **Evidence:** fmi-direct/src/main.rs lines 3017-3067: news is filled only when the stop's flag set is not within any kept set of its line of gains (`dive`), from `r.changed`, without toggles. Check on the tree: 1,830 stops show in their own `novel` labels a flag set to non-zero that is a news key elsewhere, yet it is absent from their cumulative news. 4,159 stops have truncated label lists (627 of the 1,038 path stops, per the earlier route report).
- **Why it matters:** A second arrival at the same facts is either dropped by the search or kept without news. The tree therefore cannot show alternative ways to the same progress, and every offline equality test under-reports. The true fact sets must be read again from the engine.

### 3. True state equality needs the engine, and the digest alone is too strict for re-routing. The practical test has three layers: digest (exact, expected almost never equal across time), masked facts plus position (the working equality), and replay of the re-timed rest to the end from boot (the only acceptance).

- **Evidence:** The bridge's Digest command (wire 0x98, patch 0007, patches/0007-scumm-speedrun-input.patch lines 832-878; `Engine::digest()` in fmi-engine/src/host.rs:1050) hashes the whole save stream (about 67 kB: every variable, actor, running script and local) plus the RNG, mouse and key registers, skip switches and CD and sound state; frame and tick counters are left out. E013 gate B4 (experiments/E013-robust/results/refuse/README.md): 0.18-0.27 ms per digest, and 200 of 200 consecutive idle frames differ. Existing uses: fmi-shorten/src/movie.rs compares digests at step completions between two launches (verification); fmi-explore/src/afford.rs:860 shares waits between sibling trials of one stop (1,379 of 4,831 trials). The direct search never calls it. Status already reports the RNG, and fmi-shorten/src/label.rs:384 has twins with a changed RNG.
- **Why it matters:** Equal digests guarantee an equal future but will be rare between two visits at different times (clocks, CD timer, RNG). A re-router must merge by facts with self-changing keys masked (measured by an idle fork, as the search does for its `world`), and accept only by replay. Exact-digest cuts should be counted but not relied on.

### 4. Cost of reading true state. The end path costs about 5 seconds. All 58,276 stops cost about 30 minutes of one core if the tree is walked with forks, against 28 hours if each stop is replayed from boot.

- **Evidence:** Measured now on the laptop with the frozen binary (`high9 forkbench ... --from leg02/top.jsonl 22320`, 300 rounds at frame 92,860, nice 10): fork 4.46 ms, one frame after a fork 1.37 ms, 100 frames 5.80 ms (0.045 ms per further frame), facts dump 0.79 ms, engine 52 MB resident. End path: one replay (about 3.2 s for 108,830 frames) plus 1,038 stops x about 1.1 ms (facts and digest). All stops from boot: the stops' frames sum to 3.38e9, at 3 s per 100k frames = 28.2 h. Tree walk: each stop is its parent's fork plus its own events; own-trial frames sum to 31.24 M (0.045 ms each = 23 min) plus 58,276 x 6.8 ms (fork, first frame, facts, digest) = 6.6 min. 7,926 stops have children, 50,350 are leaves, depth up to 1,037.
- **Why it matters:** A full re-read of the tree fits one short laptop run (about 5-6 minutes on 6 workers) and turns every proxy bound below into an exact count. It is new optimizer code over fmi-engine; the search binary is untouched. Facts must be stored as differences from the parent (a full dump is about 400 kB per stop).

### 5. (a) Between consecutive gains the tree holds almost no shorter way. With progress defined as a change of objects or news, 4 of 257 segments have an earlier equal stop under the same ancestor, worth 233 frames in all (0.2% of the route).

- **Evidence:** End path to the true end (bit 565 at frame 108,830, tick 657,813): 106,102 frames after first control, 257 progress stops, median segment 177 frames, largest 4,905, ten largest 29,203. Level rises only (57): 32 segments have an earlier stop with the same object set under the same ancestor (2,193 frames, 2.1%), but only 1 of those also holds the same news (96 frames) and 3 hold at least the same news (274 frames). In 251 of 257 segments the path's stop is the only first arrival at its facts. At the level of single actions: for 33 progress trials a cheaper kept trial won the same facts from the same room, 818 frames in all. Scripts a.py, a2.py in the rr2 folder.
- **Why it matters:** This is so by construction (novelty per line, news at first arrival, highest level first), not because the path is near-shortest. Picking among kept stops gains under 1%. A shorter way between two gains has to be made new: by direct walks, by dropping steps, or by a fresh search of that stretch.

### 6. Solving the recorded graph as it stands. If room+objects+news were true equality, the shortest path over all kept stops is 46,841 frames against 106,102. Nearly all of that saving is the end path's own returns to an already-held state (53,662 frames); stops off the path add only 5,599.

- **Evidence:** Dijkstra over stops merged by key, edges = the tree's trials with their frame cost (d.py). With the search's probe padding removed (66 frames on each `~` stop): the route is 79,768, path-only merge 42,342, whole tree 36,676. Adding measured room-to-room walks as edges at fixed facts: 32,164 (median walk cost) and 27,545 (best measured cost). Merging by objects+news alone (no room, so no travel at all) leaves the 257 progress trials themselves: 31,068 frames, 20,970 without padding.
- **Why it matters:** The useful content of the tree for re-routing is the list of progress trials and a table of measured walks, not alternative branches. It also gives the hard floor for this set of progress steps: about 21,000 frames (35 minutes at 6.05 ticks a frame) with zero travel.

### 7. (b) Travel. Room changes with no gain take 34,181 frames (32% of the route). Walking directly from each progress stop to the room of the next progress trial, at costs measured in the tree, needs about 13,300 frames: a saving of about 20,900 frames (19.7% of the route, about 35 minutes).

- **Evidence:** Path to bit 565 split by step: 257 progress trials 31,068 frames (20,970 without padding); 403 room-change steps with no gain 34,181 (none carries padding); 377 in-room steps with no gain 40,853 (24,617 without padding). edges.jsonl holds 134 distinct working ways with no cost; the costs come from nodes.jsonl: 16,660 trials that changed room, over 371 ordered room pairs and 765 (entered from, room, exit to) triples. Direct travel, entry-keyed: 13,280 frames. It is 12,988 to 16,238 depending on which transitions are admitted (all; single-exit only; only those seen with no object the route lacks then; only those seen with exactly the same objects), so the saving is 17,944 to 21,192. With every walk at its best measured cost: 6,778 to 11,744. Spread of a walk's cost: median 37 frames per room pair, 9 frames when keyed by the entry (b.py, b2.py).
- **Why it matters:** This is the largest re-routing gain that needs no reordering and no new action, and the walk table already exists. Keying walks by where ego entered is needed, exactly as the Part I optimiser found.

### 8. The other large pool is the 377 in-room steps with no recorded gain: 24,617 frames without padding. Two thirds of it sits in rooms the route then leaves without progress.

- **Evidence:** 7,809 frames (98 steps) lie in the progress trial's own room after the last arrival and may prepare it. 16,808 frames (279 steps) lie in rooms left without progress; 205 of those changed some world atom (object state, class, toggled bit, variable) without news, 13,124 frames; 72 are walking or sight only, 2,822. In the guide (experiments/E027-direct/guide/guide-end.json) 249 of the 533 path news keys are tested by some script; 101 of the 257 progress trials set only keys no script tests (11,040 frames with padding).
- **Why it matters:** Whether a step with an unrecorded change is needed cannot be told from the files. It needs a drop test in the engine. The pool bounds the fixed-order result between 34,250 frames (all dropped) and 58,867 (all kept), centre about 42,000 (only the preparing steps kept).

### 9. (c) Order of gains. The tree shows independence for about 2% of pairs. It explored one order, so it cannot say which gains may be reordered. The possible gain from reordering is also modest: about 3,000 to 7,000 frames on top of direct walks.

- **Evidence:** Objects: 59 of 73 were gained from one prior object set only; 52 of 2,608 ordered pairs (earlier, later) are shown independent (the later object was gained on some branch without the earlier one); 12 objects have any such evidence. All 606 facts (533 news keys, 73 objects): 3,988 of 182,452 pairs (2.19%); 211 facts are recorded as won only on the end path; 110 of 257 progress stops could move at least one slot earlier, at most 47 slots. Travel under free order: the 257 progress trials start in 64 rooms, in 138 separate visits; a nearest-neighbour tour over the 64 rooms costs 5,217 frames at best measured costs against 6,778 for the fixed order at the same costs (c.py, c2.py, b2.py).
- **Why it matters:** Reordering needs precedence the tree does not hold, and its ceiling is small next to direct walks (about 21,000 frames) and dropped steps (up to 24,600). It should come after them, with precedence learned by engine tests, not read from the tree.

### 10. Calculated bound for re-routing over what the search explored. Same progress steps, same order, direct walks, re-timed: 57 to 99 minutes, centre about 71, against 178 minutes now. That is 45% to 68% shorter. It cannot reach 21:01 by itself: the 257 progress trials alone take 35 minutes with no travel.

- **Evidence:** At 6.046 ticks a frame (641,492 ticks over 106,102 frames): route 178.2 min; without probe padding 79,768 frames = 134.0 min; plus direct walks with every in-room step kept 58,867 = 98.9 min; centre 42,059 = 70.6 min; every no-gain in-room step dropped 34,250 = 57.5 min; progress trials only 20,970 = 35.2 min. Target 21:01.483 = 75,689 ticks, about 12,500 frames at 6 ticks a frame or 14,800 at 5. Evaluation references only (never inputs): the hand no-slide run is 19,859 frames from boot (runs/anypercent/verify-b1/verify.json, 5.09 ticks a frame, 1,371 clicks and 183 keys); the 21:01 run is 14,820 frames (runs/anypercent/m2n-verify/verify.json). full5's progress trials alone are longer than the whole hand no-slide run.
- **Why it matters:** The owner is right that the gain is far more than 10%: re-timing plus re-routing over explored material is worth about 60%. The last factor of 3 to 5 down to 21 minutes must come from what the tree does not hold: fewer progress steps (which facts the end really needs), cheaper new actions between needed facts, the timer glitch, walking, and the slide family.

### 11. How the time-cost model can be built with no hand-written part, and what replaces the Part I model. Predicates become engine facts, operators become the search's own trials, costs are measured as before, and preconditions are learned by engine tests.

- **Evidence:** Part I precedent (docs/optimization.md): a hand-written PDDL model, Fast Downward A* with LM-cut, 45 plans at 42.9 s each, 67 actions, 22,292 mean ticks on 30 held-out seeds; measured costs beat the unit-cost plan by 7.1% (23,988); costs keyed by ego's start position (103 tokens derived from the plan: entry from a room, or the last object acted on) predicted within 22 ticks where pooled costs were off by up to 275; a walk's cost had zero variance for a given entry; unmeasured pairs got an optimistic cost and were then measured; the winner was chosen by measurement. Here: (1) facts = world atoms some trial changed and that do not change by themselves, read by the tree walk; (2) actions = each (room, trial name) with a non-empty fact difference, effect = the difference with adds and deletes; (3) cost = ticks from control to control, keyed by the same entry tokens; (4) travel = the 765 measured entry-keyed walks, more measured on demand; (5) preconditions start as the facts held at every observation (safe) and are relaxed by single drop tests along the route (257 tests of at most about 3.6 s each, about 15 CPU-minutes) and by earliest-stop probes; the guide's writers map (778 atoms to their writing scripts) gives static hints.
- **Why it matters:** One recommendation for the plan: build the route as progress trials plus direct walks in the found order first, then drop tests, and only then ordering. Fixed order is a plain Dijkstra per segment on the room graph. Ordering with learned precedence is a sequential ordering problem (asymmetric TSP with precedence) over at most 138 room visits: exact inside small independent groups, insertion and Or-opt moves otherwise, each move accepted by replay. A whole-game A* with LM-cut is about four times Part I's action count and should be split at stops that need every earlier fact. The model proposes and ranks; the engine decides.

### 12. Pitfalls of a fact-level model, each seen in full5.

- **Evidence:** Random draws: a draw can be stored outside the recorded keys and used much later (the critique's case: four variables written at frame 3,081 and read at frame 20,735); one room took 13,200 ticks over 21 visits because of drawn layouts; any reorder or cut changes the count of draws before later ones. Timers: 33 wait trials on the path (15 of 50, 11 of 200, 7 of 800 frames); one stop reached the same labelled state 806 frames earlier without its 800-frame wait. State the facts do not show: locals of running scripts, actor positions, the inventory's page and order (it changes which clicks select an item after a reorder), camera, CD and sound state, the input-on counter; 205 no-news steps changed a world atom. Non-monotone facts: toggles, objects given away, counters and money, so effects need deletes and numbers. One-way changes of the room graph: a walk measured early may not exist later (the admitted-transition variants differ by 3,250 frames). Position: walk costs spread by a median 37 frames per pair and up to 806 at the 90th percentile unless keyed by entry.
- **Why it matters:** The model's cost is a surrogate and its preconditions are guesses. Every plan must be realised in the engine and replayed from boot; a failed step must feed back as a learned precondition or a re-measured cost, as the Part I loop did. Stretches ruled by draws or timers are better treated as one measured block, or re-searched by the frozen search binary, than modelled.

## Open points

- How many path stops are equal by digest, and how many by masked facts plus position? Not measured: no built tool prints digests along a replay. One replay of the end path (about 5 s) answers it; I expect fewer than 10 digest-equal pairs because 200 of 200 idle frames differed in E013.
- Which of the 257 progress trials and 606 facts does the end need? This decides whether the route can go below the 35-minute floor of its own progress steps. It needs drop tests in the engine; the files cannot tell, and the guide's static map is only a hint (101 trials set no tested key).
- Which of the 279 in-room steps in rooms left without progress (16,808 frames) are needed for a hidden change (205 changed a world atom without news)?
- Can the optimizer re-make a trial by its name (verb and object ids) from another position and state? E024's forward pass stopped at step 5 of 12 on Monkey Island walking. Direct walks, drop tests and reordering all depend on this executor; fmi-explore's offer code gives click points by id, but the realiser lives inside the frozen search's main.rs.
- Are the measured walks valid at the facts where the re-router wants them? The room graph changes with progress (admitting only transitions seen with the same objects costs 3,250 frames more). Each direct walk needs one engine check.
- True precedence between gains: the tree shows 2% of pairs. Single drop tests give direct dependencies; pairs and longer chains need ddmin or earliest-stop probes, whose cost is not yet measured.
- Ticks per stop are not in the files (frames only). The bounds use the trace's 6.046 ticks a frame; under the timer glitch frames and ticks part ways and costs must be measured in ticks.
- How much do random draws move when the route is re-routed? The RNG is in Status but was not read here. Stretches ruled by draws (a room with 21 visits and 13,200 ticks, the fights, a combination drawn at frame 3,081 and used at 20,735) may need a fresh search with the frozen binary instead of the model.
- Whether a whole-game ordering problem needs an outside solver, or splitting at stops that need every earlier fact keeps each piece small enough for exact search; this depends on the learned precedence graph.
