# Autonomous glitch discovery

A research report made for E031's plan (2026-11-16) by a reading agent; its claims were used in the plan after the plan's critics checked them. Evidence paths are as the agent gave them.

## Findings

### 1. Calculated bound for this topic: the owner's target (beat 21:01.483) cannot be reached without the item-slide family, even with CD track 6 removed. Glitches that general scans find with near certainty (logo speed glitch, skip timing, random-draw delays) are already inside both hand-routed anchors.

- **Evidence:** paper/claims.md lines 8-10 and docs/anypercent/overnight.md lines 11-24: no-slide run 1681.413 s (28:01.4), 25:51.5 once the last card's 129.9 s CD wait is taken off; slide run 1391.320 s (23:11.3); same route without track 6 1261.483 s (21:01.483). Slide family = 28:01.4 - 23:11.3 = 290.1 s. Track 6 = 129.8 s and is a setting, not something a search finds.
- **Why it matters:** The time estimate has to be stated in tiers. If the optimizer only matches hand routing without the slide chain, the floor is about 28:01 (25:51.5 without track 6), 4:50 short of the target. The last 290 s depend on the slide being formed, carried from Part I into Part III and exploited three times (oars, monkey, feather), or on an unknown glitch of equal value. I put the autonomous chance of that whole chain under 10% within the stated compute.

### 2. The item slide as a general SCUMM v5 engine condition: a counter bracket broken by an absolute write. Player input is gated by one integer that scripts change in two ways (absolute on/off, relative +1/-1), and the gate never looks at the cutscene stack.

- **Evidence:** ScummVM tree /var/tmp/fast-mi/svm-e028/third_party/scummvm/engines/scumm: verbs.cpp:593 (checkExecVerbs returns only on _userPut <= 0); script_v5.cpp:870-891 (hard on/off assign 1/0, soft on/off add/subtract 1; 938-941 mirror the value into the engine variable VAR_USERPUT); script.cpp:1679-1734 (beginCutscene/endCutscene run the scripts named by VAR_CUTSCENE_START_SCRIPT / VAR_CUTSCENE_END_SCRIPT); script.cpp:949-976 (freezeScripts skips freeze-resistant slots unless flag >= 0x80, and raises the freeze count of every sentence entry); script.cpp:1223-1228 (a frozen sentence script does not block a new one). In this game the start script does soft-off + freezeScripts(127) and the end script soft-on + unfreeze (data/scripts-dos-cd/global/script-018.txt [0007],[0070]; script-019.txt [0007],[004B]). A hard on that runs while a soft bracket is open leaves the counter one high: 1 inside every later cutscene, 2 at rest. The cursor counter has the same shape.
- **Why it matters:** Stated this way the slide is not a game fact. The detector is 'input counter above its resting value, or above 0 while the cutscene stack is not empty', and the place to look is 'an absolute input-on write in a script that keeps running while another script's cutscene is open'. Both can be written with engine opcodes and engine variables only, no room, object or game variable number.

### 3. The logo glitch is the same class (a set-then-restore bracket that is interrupted), with a kill as the interrupter. Three more engine mechanisms sit behind the known skips: frozen scripts' timers stop, a walk order for an actor that is not in the current room moves it at once, and Esc revives the override's script wherever its children are.

- **Evidence:** script.cpp:1118-1141 (killScriptsAndResources: every room-local and object script dies at a room change, no restore runs; v5 only warns when one held an override); room.cpp:78-80 (startScene calls it), room.cpp:108-109 (the sentence stack is cleared only on v1-v2); script.cpp:1555-1587 (decreaseScriptDelay counts down only status == ssPaused, so a frozen paused script's delay does not run: the 'reading as a freeze' of the monkey skip); actor.cpp:870-876 (startWalkActor, version <= 6: an actor not in the current room gets its position set to the target, the oars skip's teleport); script.cpp:1736-1756 (abortCutscene sets the override script running with freeze count 0). input.cpp:594-615 even carries an engine workaround for another game where skipping one cutscene skipped a later sequence and left a script running.
- **Why it matters:** One detector family covers both root glitches of this game: index brackets (a value changed and later restored, or soft-off/soft-on) and watch for interference inside them, by a kill of the owning script or by another script's absolute write. The other three mechanisms give three more observable signals: a timed window that lasts longer than its twin, ego absent from the room while input is on, and state that differs by the frame of a skip.

### 4. Measured baseline on full5: the anomaly signals are silent on the whole found route, so they work as novelty signals with no false alarms there.

- **Evidence:** I replayed full5 from boot once with the bridge's existing per-frame log (SPEEDRUN_FRAME_LOG=1 through a wrapper; high9 verify, ok, 22.3 s wall, 10.9 s CPU; log 11.7 MB): /var/tmp/fast-mi/e031-research/glitch-probe/verify-out/eng/b0/frames.jsonl, scripts an1.py and an2.py beside it. From first control (frame 2,728) to the end flag (108,830): (input counter, cutscene depth) takes only the pairs (1,0), (0,0), (0,1), (-1,0), (-1,1), (-1,2); 0 frames with input on inside a cutscene; the counter never reaches 2; 0 frames with input on and ego not in the room; stdout holds no engine warning. Input-on-in-cutscene appears only after the end flag (frames 109,100-114,978, the closing menu). The frame-length variable is off 6 in: frames 45-91 (5, 47 frames, the logo), 7,867-7,880 and 28,660-28,673 (1, 14 frames each, input off, no cutscene), 1,201 frames at 10, 36 frames at 12.
- **Why it matters:** A search can treat any new pair, any new value of the frame-length variable at a control stop, ego missing while input is on, or any engine warning as 'new' without a threshold to tune. The 75 frames where the frame length is below its normal value are a ready target list: an Esc/key scan over them is about 375 tries and contains the logo glitch (47 of the 75 frames have a live override). The two 14-frame stretches at value 1 would be a far larger speed-up if a kill were possible there; the frame log shows input off and no override, so I expect nothing, but 420 tries settle it.

### 5. Measured: the item-slide state can be formed on full5's own route with generic inputs, and the bridge's existing Status fields show it. This contradicts the earlier report and the draft plan, which called the slide undiscoverable without game knowledge.

- **Evidence:** Evaluation probe (I chose the inputs knowing the reference setup; nothing here is system input). Command: DIRECT_SEQ_VERBS=1 env $ON $MI /var/tmp/fast-mi/direct/bench/bin/high9 seq /var/tmp/fast-mi/direct/full5/leg00/nodes.jsonl 9329 OUT var:53 k,0,1 300,141,LEAD 82,175,1 210,160,1 (stop 9329 = frame 33,881, the store; steps: automatic skips off; a floor click; LEAD frames later a click on one verb slot; next frame a click on inventory slot 2). Result sampled every 5 frames for 120 frames: LEAD 16, 17, 18, 19, 20 each end at cutscene depth 0 with the input counter at 2 for all 22 samples; LEAD 2-15 and 21, 23 return to 1. Inventory slot 5 with LEAD 19 gave a cutscene still open after 120 frames with input on for the last 60. With the search's automatic skips left on, LEAD 17-19 give nothing. At the stop the slot list shows the store's freeze-resistant local script alive (started by the room's entry script, data/scripts-dos-cd/room-030-store/entry.txt [0021]; its body is a position test, hard off, walk, hard on: local-214.txt).
- **Why it matters:** Forming the slide is a depth-3 timing problem (walk target, a cutscene-starting input, its start frame) with a 5-frame window, not a deep one. An exhaustive scan at one stop is about 9 verbs x 9 slots x 25 start frames x up to 7 floor targets = about 14,000 tries, roughly 3-4 CPU-minutes. The discovery search cannot find it by construction (its skips end every reading at once, and it never acts with skips off). What stays hard is the payoff, not the state.

### 6. A static filter over the scripts, using opcode kinds only, narrows where to run that scan: absolute input-on writes inside scripts that are started freeze-resistant.

- **Evidence:** Python pass over data/scripts-dos-cd (1,752 files): 52 hard input-on sites in 44 scripts, 26 hard input-off sites, 5 soft pairs, 315 cutscene starts in 225 files. 22 global and 90 room-local scripts are ever started freeze-resistant. Only 8 scripts are both: globals 60, 92, 93 and locals in rooms 25, 30, 31, 38, 42; 3 of them open no cutscene of their own (global 93, room 30 local 214, room 42 local 205). The two rooms where the reference route forms a slide (30 and 25) are both in the 8. full5's route enters those five rooms 32 times (room 25 x10, 30 x5, 31 x4, 38 x12, 42 x1). 59 of 1,029 object scripts open a cutscene (55 with the kind that leaves a walk alone); the route holds one such object from frame 3,312, two from 20,735, four from 63,043, eight from 82,766.
- **Why it matters:** The scan runs at 32 route visits instead of 625 room entries, and a live check in the state dump (is one of the 8 scripts in a running slot?) prunes further. Bound: 32 x 14,000 tries x about 15 ms = about 1.9 CPU-hours, 15-30 minutes on the laptop's 8 threads. Honest caveat: I designed this filter knowing the slide exists, the same limit the critique put on the logo scan.

### 7. Verdict on each proposed signal, and what the bridge shows today. Five are real and already observable; two need a small new read-only observation; one I reject.

- **Evidence:** (1) Input accepted while a cutscene runs: real; Status carries up and cs at every stop (speedrun_control.cpp:155) and the frame log every frame (speedrun_bridge.cpp:640-657). (2) Counter above rest: real; also usable as a run stop condition through the engine variable VAR_USERPUT (CondKind::Var, fmi-core lib.rs:658-671). (3) Ego not in the room while input is on: real; Status has the ego field only when ego is in the room. (4) Frame-length variable changed at a control stop: Status v19. (5) Frozen scripts, pending delays, overrides per slot, cutscene depth per level: the state dump's slots and cutscene blocks; two live sentence-script slots (one frozen) can be read from it. (6) Script killed mid-way: only inferable by diffing dumps around a room change; the exact (script, offset, held override) at the kill needs a hook. (7) Sentence stack across a room change and the popped sentence's objects: not exposed (only the blocker name sentence_queue, 1,649 normal frames on full5). (8) 'Sentence executed in another room than it was built': rejected as a main signal, v5 guards it (script_v5.cpp:3451 does nothing for an object not found; script.cpp:122-125 warns 'Code for object not in room' and returns; object.cpp:549-553 returns 255); the warning itself is a free signal. Unreachable-object actions are a game-script check, usable only as a per-object distance feature from the script-run log plus ego position.
- **Why it matters:** The first experiment needs no engine patch: Status, run conditions and the frame log are enough to census the route and to detect the slide and the speed glitch. One practical gap forces a patch later: a forked child closes the frame log (speedrun_control.cpp:201-203), so inside trials only stops are seen; an anomaly that opens and closes between two stops is missed unless the trial is stepped frame by frame.

### 8. Proposed new observation (patch 0014, read-only, off unless asked): an in-memory anomaly event list that also works in forked children, fetched by a new wire command.

- **Evidence:** Events, each with frame, script number, code offset: hard input or cursor write while the cutscene stack is not empty or when the old value was not 0/1 (hook in o5_cursorCommand); a slot killed before its end with its override count, freeze count and delay (killScriptsAndResources, stopScript, chainScript); abortCutscene with the level and the scripts still alive; a sentence popped, with whether its objects are in the room, the number of frozen slots and cutscene depth (checkAndRunSentenceScript); a walk order for an actor not in the current room (startWalkActor); engine warnings by site. Precedent for 'switch off = same bytes': patch 0007's input log and patch 0013 (the commit log says the gate's six digests were unchanged). The frozen binaries never send the new command and Status keeps its layout.
- **Why it matters:** It keeps hard constraint 1 (search code and behaviour untouched, gate must pass) while giving trials exact, cheap events instead of per-frame polling. The bridge already records for each injected input whether it was dropped at the gate or taken and what it wrote (speedrun_inputs.cpp:225-240), so 'input taken at cutscene depth > 0' needs only the join with Status.

### 9. Where to try, with counts measured on full5 and unit costs from the run's own summaries. All discovery scans together fit one laptop run of one to two hours.

- **Evidence:** Unit costs (/var/tmp/fast-mi/direct/full5/leg00..03/summary.json): 9,725,491 trials, 82,422 worker-seconds = 8.5 ms a trial; 624,352,814 trial frames in 23,180 s = 37 microseconds a frame; fork 5.6 ms on the loaded VM (1.4 ms measured on the laptop, study guide 02-bridge-core.md section 11). Scans: (A) keys at frames where the frame-length variable is below normal: 75 frames x 5 inputs = 375 tries; whole boot, 2,728 frames x 5 = 13,640 tries, at most 23 CPU-minutes. (B) Skip timing: 574 cutscene intervals before the end flag (10,933 frames; median 4, p90 43, max 1,300), Esc at each of the first 60 frames or never = 9,522 tries, plus 1,843 text skips x 5 delays. (C) The bracket race of the slide: 32 visits x 14,000 = 448,000 tries, about 1.9 CPU-hours. (D) Inputs while the click gate is open but the search does not act (ego walking, a sentence running): 34,757 frames in 1,478 intervals x about 40 pruned inputs = 1.39 million tries, about 4.6 CPU-hours, or a quarter of that sampling every fourth frame first. fmi-engine already has fork_each (host.rs:951) and fmi-shorten's scan.rs uses it to stand an engine at every frame of a window.
- **Why it matters:** These are exactly the frames the discovery search never touches: before first control, inside cutscenes, mid-action, and any frame with a key or with skips off. Scans A-D total about 7-8 CPU-hours. The open-ended cost is not finding anomalies but valuing them.

### 10. The frozen search cannot value a slide state by itself, but it can be started from any anomaly state without a code change. A targeted explorer in the optimizer is needed for the frames it will not use.

- **Evidence:** fmi-direct main.rs:701-703: takes_click needs cutscene depth 0, so the search never clicks inside a cutscene even when input is on. The bridge's idle rule names 'cutscene' as a blocker (speedrun_state.cpp:480-483). The bridge's automatic Esc is refused while input is on (speedrun_skips.cpp:114-115), so in a slide state cutscenes run unskipped unless the optimizer schedules Esc itself (raw key events exist: esc, space, enter, printable characters). The search's --from reader accepts key events and skips events with a spare list (fmi-explore events.rs:29-40, used at main.rs:986-990), so a one-line stop file whose movie contains keys and skip switches is a valid start.
- **Why it matters:** Valuation splits in two. Anomalies that change what normal play can reach (an object owned early, a room entered early, a changed frame length) can be valued by the unchanged high9 with --from, one key in --until and a --stops bound; full5 averaged 1.83 s of wall time per expanded stop on the VM, so a 200-stop probe is 6-15 minutes and only 10-20 probes fit a run. Anomalies whose use is inside cutscenes need the optimizer's own per-frame explorer with the stop rule 'input counter above 0'.

### 11. Design for payoff that comes much later: keep anomaly states as graph nodes with a tick debt, and value them in four steps of rising cost.

- **Evidence:** Step 1, persistence profile (one replay, seconds): continue the route's own inputs from the anomaly state and record how many frames, rooms and cutscenes the anomaly survives; in this game any dialogue's hard input-on resets the counter (docs/anypercent findings and the earlier report), so many slide states die within one or two steps and can be dropped at once. Step 2, window scan: at every surviving frame the baseline could not use, try about 40 pruned inputs; reward a route milestone key held earlier in ticks or out of order (full5's chain has 554 news keys on 219 gaining stops), a new anomaly signature (for example ego leaving the room), or a room entered out of route order. Step 3, frozen-search probe from the few best. Step 4, the only number that counts: re-find the rest of the route and verify from boot to the end flag. For carrying an anomaly through rooms, use Go-Explore cells keyed by (milestone level, room, input counter, cutscene depth, top cutscene script, ego in room, frame length) and expand the cells where the anomaly is still alive.
- **Why it matters:** A step-local judge (E024's earliest completion) rejects every setup, because the setup costs ticks (the reference run's slide setup cost 22.5 s). The debt rule plus the persistence profile makes the keep-or-drop decision cheap and general. The prize size for a sequence break is read from the route itself: the ticks between the skipped milestones.

### 12. Feasibility by known glitch, using a depth count (how many separately timed inputs must all be right). Depth 1-3 is findable by exhaustive scan; depth 5 and more is not, unless every intermediate step shows a novelty signal.

- **Evidence:** Logo speed glitch: depth 1, 375 to 13,640 tries, near certain; fails only if the judge counts frames instead of ticks. Skip-timing effects: depth 1, about 19,000 tries, near certain to find what exists. Random-draw steering (catacombs 59 s to 12 s in docs/anypercent/findings.md): depth 1 per draw, near certain. Slide state in the store: depth 3, shown by the probe; I put 80-90% once the scan exists. Slide state at the village with a held book-like item: same scan, about 50% (not probed). Feather skip: needs a live slide on the ghost ship, a verb and pointer set before the cutscene and one click inside it (about 2,700 tries per cutscene once in the state); 10-15% overall, worth 5.5-15 s. Position-dependent animation skips (necklace 2 x 20 frames, head about 4 s) and the forest map teleport: one input or one standing point each, a few thousand tries, about 50% each. Oars skip: slide carried into Part III, a 16-frame window, an exact pixel; a few hundred tries if the slide is alive there, about 2% overall. Monkey skip: 4-5 timed inputs plus a camera precondition, on the order of 10^8 blind combinations; under 3% unless 'a timed window held open longer than its twin' is rewarded as a step. Carrying the slide from Part I to Part III: 6-10 timed steps over several rooms; under 10% even with the persistence cells. Credit Early was already found by the search.
- **Why it matters:** Expected value: the first tier is certain but already inside the 28:01 anchor; the second tier adds seconds to tens of seconds; the 290 s tier has an expected value of about 15-30 s at these odds. The plan should promise tiers one and two, report the slide state as a result in its own right (a glitch state found by a general scan), and treat the slide chain as a stretch goal with its own stop rule.

### 13. Prior art supports the method (state feedback on a few engine values plus restore-and-retry finds real timing glitches) and also names the hard part (use, not detection).

- **Evidence:** IJON, IEEE S&P 2020 (text extracted from https://www.gwern.net/doc/reinforcement-learning/exploration/2020-aschermann.pdf): with one annotation maximising the player's x per height, AFL solved all but 3 Super Mario Bros. levels in minutes and 'was able to find and exploit at least two' known glitches, a level exit through the ceiling and wall jumps that need one exact frame and sub-pixel position. SGFuzz, USENIX Security 2022 (https://www.usenix.org/conference/usenixsecurity22/presentation/ba): finds state variables automatically and uses their value sequences as coverage. Go-Explore for reachability testing (https://arxiv.org/abs/2209.00570): restore a stored state, take random actions, flag positions the navigation mesh does not predict; no learning; beat curiosity RL; 1.5 km map in 10 h on one machine. DIDUCE, ICSE 2002 (https://cs.fit.edu/~pkc/id/related/hangal-icse02.pdf): learn invariants from normal runs, report violations; found a timing-dependent bug. PCT, ASPLOS 2010 (https://people.cs.rutgers.edu/~sn349/papers/asplos2010.pdf): a bug needing d ordering constraints is hit with probability at least 1/(n k^(d-1)), the basis for my depth count. TASVideos common tricks (https://tasvideos.org/GameResources/CommonTricks): 'there are short periods when you can make valid game input while you are not supposed to do so'; 'Critical routines can be interrupted'. BizHawk Basic Bot (https://tasvideos.org/BizHawk/BasicBot and forum threads): random inputs over short windows against a memory value, judged useful for about ten frames. Cook et al. 2025 (https://ceur-ws.org/Vol-4090/paper1.pdf, text extracted): random input files, one input every fifth frame, rediscovered a known trick 'after a short series of runs'; they warn that 'rediscovering an existing glitch is not the same as glitch hunting' and name 'the gap between identifying a glitch, and finding a use for it'. Canonical ES on Atari (https://arxiv.org/abs/1802.08842): a score-driven search found an unknown Q*bert bug, reproduced in only 8 of 30 runs. World of Bugs (https://arxiv.org/abs/2206.11037) and curiosity agents (https://arxiv.org/abs/2103.13798) are test-coverage work with bug lists, not speed.
- **Why it matters:** Two points transfer directly. First, an oracle built from 'what the normal run never does' (DIDUCE, the navigation-mesh check) is the same idea as my zero-baseline signals. Second, our setting is easier than most of this work on one axis: exact forks and frame-exact replay make every found state reproducible, where the Q*bert bug was not. Nothing in the literature solves late payoff; the anomaly-node valuation is the part that would be new.

### 14. What can make it fail, beyond low odds on deep chains.

- **Evidence:** (1) Every scan input shifts later frames and random draws, so each accepted anomaly forces the rest of the route to be found again (E024 and the earlier critique). (2) Engine errors are fatal in a trial: script.cpp:915 ('ending with active cutscene/override'), room.cpp:62-68, script.cpp:1685/1728 (cutscene stack over- and underflow); a scan must count a dead child as that try's outcome, as scan.rs already does. (3) Soft locks: a killed cutscene owner leaves the stack raised and the counter at -1 for good; the bridge's stall record (not idle for 3,600 ticks) detects it. (4) Inside a cutscene the hover script is frozen, so room objects cannot be targeted; verb and pointer must be set before the cutscene, which adds depth. (5) Text speed: at the route's fastest text the store window was 5 frames; a slower setting widens windows but changes every unskipped line. (6) The laptop is shared; load average was 25 during my probes, so wall times are uncertain. (7) A new frame length changes the tick cost of everything; a route whose final frame length is above the starting one must be rejected (one script on the route sets 12 and restores it).
- **Why it matters:** These set the stop rules: cap valuation probes per run, drop anomalies whose persistence profile is empty, and never accept an anomaly without a from-boot replay to the end flag.

### 15. Suggested milestones for the glitch part of the plan, each a result, with predictions.

- **Evidence:** G-A, anomaly census (no patch): replay the route with the frame log, build the baseline sets; predicted result as measured here (6 pairs, 75 low-frame-length frames, 0 off-room, 0 warnings). G-B, timing-variable scan: predicted to find a control state with frame length 5 from one Esc in boot frames 46-92; stop if no try changes the value. G-C, bracket race scan at the 32 visits: predicted to reach counter 2 at rest in the store visits from frame 20,735 on (one cutscene-opening object held), at least one hit per such visit; stop rule: zero hits over all visits. G-D, persistence profile and window scan for every state from G-C: prediction uncertain; I expect most states to die at the next dialogue and at most a few seconds of verified gain; stop after the budgeted probes. G-E, patch 0014 with the gate, only if G-D shows anomalies opening and closing between stops. The slide chain (carry, oars, monkey) is a stretch lane behind G-D with its own budget.
- **Why it matters:** G-A to G-C cost under two laptop hours, need no engine change, and give a paper-grade result either way: a general scan that reaches both root glitch states of this game, or a measured reason why not. The draft plan (scratchpad/e031/plan.md, glitch table) lists the slide family as out; G-C moves forming the state in, and keeps the payoff chain out of the promised time.

## Open points

- How long the slide state formed at frame 33,881 (or at the visits from 20,735 and at 51,155) survives on full5's continuation, and whether any cutscene inside that span gives a route milestone earlier. Only the persistence profile and window scan answer it; I did not run them.
- Which state key makes two anomaly states the same cell for the carry search (room, input counter, cutscene depth, top cutscene script, ego in room, frame length, milestone level is my proposal); too coarse loses the carry, too fine explodes.
